dlp-access-next-cdk · infra/

Learning AWS CDK by tracing one deploy

We follow a single command from the moment you press Enter until CloudFormation has built the tables, search domain, API and website. At each step: what code runs, what CDK is doing underneath, and the CDK idea it illustrates.

The mental model

CDK is not a deployment engine. It is a library plus a CLI that lets an ordinary TypeScript program write CloudFormation templates. CloudFormation, the AWS service, still does the creating, updating and deleting. Everything in this repo's infra/ boils down to three phases:

1 · Construct

Your TypeScript runs. Each new Something(this, 'Id', props) adds a node to an in-memory tree. Nothing touches AWS.

2 · Synthesize

CDK walks the tree and writes a cloud assembly to cdk.out/: one CloudFormation template per stack, plus zipped “assets”.

3 · Deploy

The CLI uploads the assets to S3 and hands each template to CloudFormation, in dependency order. CloudFormation makes the API calls.

The command we will trace is the one in CLAUDE.md that deploys an environment's backend: 

cd infra
npm run deploy -- -c env=dev -c account=$ACCOUNT -c userPool=us-east-1_XXXX

Along the way we will also look at what changes when you add -c branch=… to get a Web stack.

1

npm run deploy: a guard in front of CDK

Before CDK runs · infra/bin/deploy.ts

package.json maps deploy to ts-node bin/deploy.ts. This script is the project's own; plain npx cdk deploy would skip it. It does four things:

  1. Parses the arguments (deployArgs, contextFromArgs). It merges the context block of cdk.json with your -c key=value flags, the same precedence CDK itself uses.
  2. Runs the app's own validation: planApp(optionsFromContext(...)). This is the exact function the CDK app calls in step 4, so a typo like -c env=staging fails here before anything slow happens.
  3. Checks what is already deployed (lib/deploy-check.ts) with the aws CLI, listing each stack as create, update or busy and warning about risky changes.
  4. Asks for confirmation, then spawns the real thing:
infra/bin/deploy.ts
const result = spawnSync('npx', ['cdk', 'deploy', '--all', ...args], { cwd: INFRA_DIR, stdio: 'inherit' });
CDK idea: the app can't ask questions

The CDK CLI runs your app with stdin closed, so an interactive prompt can't live inside the stacks. That is why this confirmation is a separate wrapper script.

2

The CDK CLI reads cdk.json

Before CDK runs · infra/cdk.json

cdk deploy first needs a cloud assembly, so it has to run your program. It finds out how from cdk.json:

infra/cdk.json (abridged)
{
  "app": "npx ts-node --prefer-ts-exts bin/appsync.ts",
  "context": {
    "@aws-cdk/aws-iam:minimizePolicies": true,
    "@aws-cdk/core:defaultCrossStackReferences": "strong",
    ...
  }
}
  • app is just a shell command. The CLI runs it as a child process and passes along your context and an output directory through environment variables (CDK_CONTEXT_JSON, CDK_OUTDIR). This is why CDK commands must run from infra/: elsewhere there is no cdk.json, hence “--app is required”.
  • context holds key/value settings visible to the app. The @aws-cdk/... keys are feature flags: switches that opt a project into newer, sometimes breaking, default behaviors. They live in the repo so every machine synthesizes identical templates.

A third source of context, cdk.context.json, caches lookup results. We will meet it in step 9.

3

new cdk.App(): the root of the tree

Construct phase · infra/bin/appsync.ts
infra/bin/appsync.ts — the entire entry point
const app = new cdk.App();
buildApp(app, optionsFromContext((key) => app.node.tryGetContext(key)));

Six lines, but they set up everything that follows.

Concept · the construct tree

Every CDK object is a construct, and every construct has exactly one parent (its scope) and an id unique among its siblings. App is the root. Stacks are children of the app; resources are children of stacks; higher-level constructs have their own children. Each construct is reachable through .node, which knows its path, children, dependencies and context.

app.node.tryGetContext('env') reads -c env=dev. Any construct can read context, but this repo reads it once at the root and passes plain values down. That makes the stacks easy to test without the CLI.

When this file finishes running, the App's synth() runs automatically (the App registers itself to synthesize on process exit when the CLI has set CDK_OUTDIR). So the whole construct phase is simply: run buildApp to completion.

4

planApp: it's just TypeScript

Construct phase · infra/lib/app.ts

Before any AWS concept appears, buildApp calls planApp, which is pure logic: validate the account ID, resolve the environment, decide which stacks exist.

infra/lib/app.ts
const config = resolveEnvironment(options.env, production);   // lib/environments.ts
...
const prefix = `DlpAccessNext-${config.name}`;
const provision = options.branch === undefined || backend === 'provision';
...
dataStackName: provision ? `${prefix}-Data` : undefined,
apiStackName:  provision ? `${prefix}-Api`  : undefined,
authStackName: provision ? `${prefix}-Auth` : undefined,
webStackName:  branch === undefined ? undefined : `DlpAccessNext-Web-${branch}`,

resolveEnvironment('dev', false) returns an EnvironmentConfig that merges dev's settings (region us-east-1, RemovalPolicy.RETAIN) with the standard sizing (one t3.small.search node). A feature environment like f-search gets dev's settings except RemovalPolicy.DESTROY.

CDK idea: use the language, not a template language

In raw CloudFormation, “three environments with slightly different settings” means parameters, conditions and Fn::If. In CDK it is an object literal and a function. The decision happens at synth time, so each environment's template is plain and fully resolved: dev's template contains "DeletionPolicy": "Retain", with no conditions.

Context values come in as strings: -c production=true arrives as "true". That is why booleanContext accepts both forms.

5

new DataStack(app, id, props)

Construct phase · infra/lib/app.ts → buildApp
infra/lib/app.ts
const env = { account: plan.account, region: config.region };

data = new DataStack(app, plan.dataStackName, { env, config });
api  = new ApiStack(app, plan.apiStackName, {
  env, config,
  tables: data.tables,
  searchDomain: data.searchDomain,
});
Concept · the (scope, id, props) signature

Every construct constructor takes the same three arguments. scope is the parent (app here, this inside a stack). id names it within that parent; for a Stack, it also becomes the CloudFormation stack name, e.g. DlpAccessNext-dev-Data. props is a typed bag of settings. DataStackProps extends StackProps, which adds the repo's own config to CDK's standard stack options.

Concept · stack environments

Passing env: { account, region } makes the stack environment-specific: the template is pinned to that account and region, and CDK may query the account at synth time (lookups) and use real availability zones. Without env, a stack is “environment-agnostic” and those features are off. This repo always pins it, which is why -c account is required.

Note the highlighted lines: ApiStack receives objects from DataStack, not names. That turns out to matter a lot. See step 7.

6

Inside DataStack: L2 constructs

Construct phase · infra/lib/data-stack.ts

6a. Tables: one line of intent, a page of CloudFormation

The constructor loops over MODELS and creates seven dynamodb.Tables. Here is what you write, and the CloudFormation that synth produced for Archive in a sample f-demo environment:

You write (data-stack.ts)
const table = new dynamodb.Table(this, `${model}Table`, {
  tableName: tableName(model, config.name),
  partitionKey: { name: 'id', type: STRING },
  billingMode: PAY_PER_REQUEST,
  stream: NEW_AND_OLD_IMAGES,
  deletionProtection: retain,
  pointInTimeRecoverySpecification:
    { pointInTimeRecoveryEnabled: retain },
  removalPolicy: config.removalPolicy,
});
for (const index of GLOBAL_INDEXES[model]) {
  table.addGlobalSecondaryIndex({
    indexName: index.indexName,
    partitionKey: { name: index.partitionKey, type: STRING },
    projectionType: ProjectionType.ALL,
  });
}
CDK emits (DlpAccessNext-f-demo-Data.template.json) 
"ArchiveTable4E5864BF": {
  "Type": "AWS::DynamoDB::Table",
  "Properties": {
    "AttributeDefinitions": [
      { "AttributeName": "id", "AttributeType": "S" },
      { "AttributeName": "identifier", ... },
      { "AttributeName": "collectionArchivesId", ... }
    ],
    "BillingMode": "PAY_PER_REQUEST",
    "GlobalSecondaryIndexes": [ ...2 indexes... ],
    "KeySchema": [{ "AttributeName": "id", "KeyType": "HASH" }],
    "StreamSpecification":
      { "StreamViewType": "NEW_AND_OLD_IMAGES" },
    "TableName": "Archive-dlpnext-f-demo"
  },
  "UpdateReplacePolicy": "Delete",
  "DeletionPolicy": "Delete",
  "Metadata": {
    "aws:cdk:path": "DlpAccessNext-f-demo-Data/ArchiveTable/Resource"
  }
}

Things to notice:

  • CDK filled in AttributeDefinitions from the partition keys of the table and its indexes. In raw CloudFormation you would maintain that list by hand.
  • The construct is mutable until synth. addGlobalSecondaryIndex is called after construction and still lands in the same resource. Nothing is “sent” when you call new.
  • The logical ID ArchiveTable4E5864BF is the construct path plus a hash of it. CloudFormation identifies resources by logical ID, so renaming or moving a construct's id replaces the resource. For a table, that means a new, empty table.
  • removalPolicy became DeletionPolicy. For f-demo it is Delete; for dev it would be Retain, so CloudFormation leaves the table behind when the stack is destroyed.
Concept · L1, L2, L3

L1 constructs (CfnTable, CfnEnvironment) are generated one-to-one from the CloudFormation spec: every property, no defaults, no helpers. L2 constructs (dynamodb.Table, lambda.Function, opensearch.Domain) wrap an L1 with sensible defaults, typed enums and methods like grant…. An L2 creates its L1 as a child called Resource, which is why the path ends in /ArchiveTable/Resource. L3 constructs (“patterns”) compose several resources; cr.Provider below is one.

6b. The OpenSearch domain

new opensearch.Domain(this, 'SearchDomain', {...}) reads its sizing straight from config.search. That is how -c production=true turns into three m7g.medium.search nodes across three AZs. Its removalPolicy is hard-coded to DESTROY, so the domain goes with the stack in every environment while the tables follow config.

6c. A Lambda with local code: your first asset

infra/lib/data-stack.ts
const indexTemplateFn = new lambda.Function(this, 'IndexTemplateFunction', {
  runtime: lambda.Runtime.PYTHON_3_12,
  handler: 'index.on_event',
  code: lambda.Code.fromAsset(path.join(__dirname, '..', 'lambda', 'opensearch-index-template')),
  environment: {
    OPENSEARCH_ENDPOINT: domain.domainEndpoint,
    ...
  },
});
Concept · assets

A template can't contain a directory of Python. Code.fromAsset tells CDK: “at synth, copy this directory into cdk.out and fingerprint it; at deploy, zip it and upload it to the bootstrap bucket; in the template, point the function at that S3 key.” The fingerprint is a content hash, so the Lambda updates only when the files change.

Concept · tokens (the most important idea in CDK)

domain.domainEndpoint is not a URL. The domain doesn't exist yet. It is a token: a placeholder string such as ${Token[TOKEN.312]} that CDK tracks. At synth it is replaced with CloudFormation's own reference, {"Fn::GetAtt": ["SearchDomainFDC494A0", "DomainEndpoint"]}, which CloudFormation resolves at deploy time. Consequences:

• You can pass tokens around, put them in strings and store them in props, and they still work.
• You cannot inspect them in TypeScript: if (domain.domainEndpoint.startsWith('search-')) is meaningless at construct time.
• A token also records which resource it came from. CDK uses that to work out dependencies automatically.

6d. Permissions by method call

domain.grantPathReadWrite('_index_template/*', indexTemplateFn);

This one line adds an AWS::IAM::Policy to the function's auto-created execution role, allowing es:ESHttpGet/Put/… on <domain ARN>/_index_template/*. CDK's grant* methods are why the synthesized Data stack has 2 roles and 2 policies you never declared.

6e. A custom resource: running code during the deploy

const indexTemplateProvider = new cr.Provider(this, 'IndexTemplateProvider', {
  onEventHandler: indexTemplateFn,
});
for (const model of SEARCHABLE_MODELS) {
  new CustomResource(this, `${model}IndexTemplate`, {
    serviceToken: indexTemplateProvider.serviceToken,
    properties: { TemplateName: `dlpnext-${index}`, IndexPatterns: [index],
                  Mappings: JSON.stringify(searchMappings(index)) },
  });
}

CloudFormation knows how to create an OpenSearch domain but not an index template inside it. A custom resource fills the gap. When CloudFormation reaches this resource, it invokes a Lambda with a Create, Update or Delete event and the properties above. lambda/opensearch-index-template/index.py then makes a SigV4-signed PUT _index_template/dlpnext-archive. cr.Provider is the L3 “provider framework”: it adds a second, CDK-supplied Lambda that handles CloudFormation's response protocol, which is why the Data stack has two functions.

Note that searchMappings(index) runs at synth time. It parses schema/schema.graphql in TypeScript and bakes the resulting JSON into the template. If the schema changes, the property changes, which triggers an Update event.

6f. Outputs

new CfnOutput(this, 'SearchDomainEndpoint', { value: domain.domainEndpoint });

Stack outputs are printed after cdk deploy and visible in the console and through aws cloudformation describe-stacks. deploy-check.ts reads them this way.

7

ApiStack and cross-stack references

Construct phase · infra/lib/api-stack.ts

The Api stack builds the AppSync API. One call wires a table into it: 

acc[model] = api.addDynamoDbDataSource(`${model}DataSource`, tables[model]);

tables[model] belongs to a different stack. Its tableName token points at a resource in DlpAccessNext-dev-Data, and one CloudFormation template can't Ref a resource in another template. At synth time, CDK notices and rewrites both sides:

Producer: Data stack gains an Output with an Export 
"ExportsOutputRefArchiveTable4E5864BF16DAEC2E": {
  "Value": { "Ref": "ArchiveTable4E5864BF" },
  "Export": {
    "Name": "DlpAccessNext-f-demo-Data:ExportsOutputRef
             ArchiveTable4E5864BF16DAEC2E"
  }
}
Consumer: Api stack imports it
"VtdlpApiArchiveDataSource00754320": {
  "Type": "AWS::AppSync::DataSource",
  "Properties": {
    "DynamoDBConfig": {
      "TableName": {
        "Fn::ImportValue": "DlpAccessNext-f-demo-Data:
           ExportsOutputRefArchiveTable4E5864BF16DAEC2E"
      }
    }, ...

CDK also records that Api depends on Data, so cdk deploy --all deploys Data first. In the sample synth, the Data stack has 18 such ExportsOutput… entries: table names, ARNs, stream ARNs and the domain endpoint.

The catch with exports

CloudFormation refuses to delete or change an export while another stack imports it. If you stop using a table in the Api stack, the Data stack can't drop the export until Api is updated first. This “deadly embrace” is the main reason the Web stack uses a different mechanism (step 9).

7a. Generated resolver code

jsResolver('Query', `get${model}`, dataSources[model], getByIdCode());

getByIdCode() (in lib/resolvers.ts) returns a JavaScript string, and appsync.Code.fromInline puts it in the template verbatim. Here is the synthesized result: 

"QuerygetArchiveResolverF3D41FAD": {
  "Type": "AWS::AppSync::Resolver",
  "Properties": {
    "ApiId": { "Fn::GetAtt": ["VtdlpApi1EE3EB61", "ApiId"] },
    "Code": "import { util } from '@aws-appsync/utils';\n\nexport function request(ctx) {\n  return { operation: 'GetItem', ... }",
    "DataSourceName": "ArchiveDataSource",
    "FieldName": "getArchive",
    "Runtime": { "Name": "APPSYNC_JS", "RuntimeVersion": "1.0.0" },
    "TypeName": "Query"
  },
  "DependsOn": ["VtdlpApiArchiveDataSource00754320", "VtdlpApiSchemaA45B1951"]
}

The loops over MODELS make 26 resolvers out of about 80 lines. Note the DependsOn, which CDK added because the resolver must wait for its data source and the schema. You rarely write ordering by hand inside a stack, because the references imply it.

7b. Implicit roles everywhere

The synthesized Api stack has 68 resources, 12 of them IAM roles and 11 policies, even though api-stack.ts declares exactly one role (EbInstanceRole). The rest come from L2 defaults: each addDynamoDbDataSource creates a service role for AppSync and grants it read/write on the table; lambda.Function creates an execution role; addEventSource(new DynamoEventSource(...)) grants the function stream-read permissions and creates an EventSourceMapping; SqsDlq grants send on the queue. Finally: 

api.grant(ebRole, appsync.IamResource.all(), 'appsync:GraphQL');

This is the only thing that lets the Next.js server call the API.

7c. Publishing a value by name

new ssm.StringParameter(this, 'GraphQLApiUrlParameter', {
  parameterName: graphqlApiUrlParameterName(config.name),   // /dlp-access-next/dev/graphql-api-url
  stringValue: api.graphqlUrl,                              // a token
});

The Api stack writes its URL into SSM Parameter Store under a predictable name. Keep this in mind for step 9.

8

AuthStack: the smallest stack

Construct phase · infra/lib/auth-stack.ts

Two ssm.StringParameters and two outputs; 3 resources after synth, counting CDK's metadata resource. It records the user pool ID and identity provider name. The pool itself is not managed by CDK.

CDK idea: a stack is a unit of deployment and lifecycle

Why a whole stack for two parameters? Because stacks are what you deploy, update and destroy as a unit. The repo's split by lifecycle is a common CDK design: Data is stateful and rarely changes, Api is stateless and changes often, Auth is configuration, and Web is per branch and disposable. Tearing down Api never risks the tables.

9

WebStack: imports, lookups and side effects

Construct phase · infra/lib/web-stack.ts (only with -c branch=…)

The Web stack shows the most CDK techniques in one file. When you add -c branch=$(git branch --show-current), buildApp creates it and, if the backend is in the same app, orders it explicitly: 

web = new WebStack(app, plan.webStackName, { env, config, branch, ... });
for (const stack of [api, auth]) {
  if (stack) web.addStackDependency(stack);
}

Why explicit? Because the Web stack holds no object references to Api or Auth, so CDK can't infer the order. It is designed to work when those stacks were deployed from a different CDK run (backend=attach), where no objects exist to reference.

9a. Code that runs at synth time

const commit = sourceCommit();                    // git rev-parse HEAD
git('archive', '--format=tar', `--output=${archive}`, commit, '--', ...pathspecs);
execFileSync('tar', ['-xf', archive, '-C', source]);
this.sourceBundle = new s3assets.Asset(this, 'SourceBundle', { path: source });

Your constructor is ordinary Node.js and can do anything: shell out to git, read files, compute. Here it exports HEAD to a temp directory and makes it an s3assets.Asset, the same asset mechanism as the Lambda code, except Beanstalk consumes it. The asset hash changes with every commit, so every new commit is a new application version.

Keep synth deterministic

Synth-time side effects are fine as long as the same inputs give the same template. Reading HEAD is deterministic per commit. Something like Date.now() in a property would make every synth look like a change.

9b. L1 constructs when there's no L2

const application = new elasticbeanstalk.CfnApplication(this, 'Application', {...});
const version     = new elasticbeanstalk.CfnApplicationVersion(this, 'Version', {
  sourceBundle: { s3Bucket: this.sourceBundle.s3BucketName, s3Key: this.sourceBundle.s3ObjectKey },
});
version.addResourceDependency(application);

Elastic Beanstalk has no L2, so this file uses the raw Cfn* classes. You lose the conveniences. Properties refer to the application by name (a plain string), not by token, so CDK can't see the relationship, and you add the DependsOn yourself with addResourceDependency. The big settings object flattened into optionSettings is just TypeScript producing the array the L1 property wants.

9c. Finding the environment by name: SSM parameters resolved at deploy time 

const apiUrl = ssm.StringParameter.valueForStringParameter(this, graphqlApiUrlParameterName(config.name));

This is the counterpart to step 7c, and the alternative to an export. It does not read SSM during synth. It adds a CloudFormation Parameter of type AWS::SSM::Parameter::Value<String> whose default is the parameter name, and returns a token that refers to it. CloudFormation looks up the current value when the stack deploys. If the Api stack was never deployed, that lookup fails: “Unable to fetch parameters”.

Export / ImportValue (step 7) SSM parameter by name (step 9)
How you write it Pass the object in props Agree on a name, read it with valueForStringParameter
Ordering Inferred automatically You add addStackDependency when in the same app
Across CDK apps / runs No: both stacks must be in one app Yes
Producer locked while consumed Yes (deadly embrace) No
Value updates propagate Blocked while imported On the consumer's next deploy

9d. Importing existing resources

cognito.UserPool.fromUserPoolId(this, 'UserPool', userPoolId)
iam.Role.fromRoleName(this, 'InstanceRole', ebInstanceProfileName(config.name))

from… methods create a lightweight construct that represents something that already exists. It adds nothing to the template, but it satisfies the same interface (IUserPool, IRole) as a real one, so you can attach a UserPoolClient to it or attach a policy to it. This is how the Web stack adds the ClientSecretRead inline policy to a role owned by the Api stack, and how CDK uses a Cognito pool it never manages. The I-prefixed types (dynamodb.ITable in DataStack.tables) exist so that real and imported resources are interchangeable.

9e. A context lookup: the one time synth talks to AWS

zone: route53.HostedZone.fromLookup(this, 'HostedZone', { domainName: HOSTED_ZONE }),

Unlike valueForStringParameter, this needs the answer at synth time, because the zone ID goes into the template as a literal. Here is how it plays out:

  1. On the first synth, the value isn't in context. The construct returns a dummy and records a “missing context” entry in the assembly.
  2. The CLI sees the missing entry, assumes the bootstrap lookup role in your account, and queries Route 53.
  3. It saves the answer to cdk.context.json and runs your app again, which now finds the value.

Later synths read the cache and never call AWS. The repo git-ignores cdk.context.json because the cached record contains the account ID. To refresh a stale lookup, use cdk context --reset <key>.

9f. Ordering inside a stack, explicitly

environment.node.addDependency(secretRead);

The Beanstalk environment refers to the secret's ARN, so CDK already orders the secret first, but nothing refers to the policy that lets the instance read it. Without this line, CloudFormation might start an instance before it is allowed to read the secret. node.addDependency works between any two constructs and becomes DependsOn on every resource underneath them.

10

Synthesis: the cloud assembly

Synthesize phase · cdk.out/

buildApp returns, the process is about to exit, and app.synth() runs. In order, it:

  1. Prepares the tree: applies Aspects (visitors that can inspect or modify every construct), resolves cross-stack references into exports and imports (step 7), and works out stack dependencies.
  2. Validates: constructs can register checks, and errors stop synth here.
  3. Resolves tokens: every token becomes Ref, Fn::GetAtt, Fn::ImportValue or a literal.
  4. Writes the assembly.

Running cdk synth for a sample -c env=f-demo produced:

├── tree.json                              ← the construct tree (good for exploring)

├── DlpAccessNext-f-demo-Api.assets.json

Each template also has a BootstrapVersion parameter, and manifest.json names roles like cdk-hnb659fds-deploy-role-<account>-us-east-1. Both point at the bootstrap stack: a one-time cdk bootstrap per account and region that creates the asset bucket and the roles the CLI uses to deploy. hnb659fds is the default bootstrap qualifier.

Synth is safe; use it constantly

Synth only needs credentials for uncached lookups. The backend stacks have none, so you can synth them with a made-up account ID and read exactly what would be deployed. cdk diff compares that output with what's live.

11

Deploy: assets, then CloudFormation

Deploy phase · CDK CLI → S3 → CloudFormation

Now the CLI works from cdk.out alone. Your TypeScript is finished.

  1. Check bootstrap: read /cdk-bootstrap/hnb659fds/version and refuse if it's older than the assembly requires.
  2. Publish assets (*.assets.json): zip each asset.* directory and upload it to cdk-hnb659fds-assets-<account>-<region> as <hash>.zip, using the file-publishing role. The templates themselves are uploaded too. A hash that already exists in S3 is skipped.
  3. Deploy stacks in dependency order. --all selects every stack, and the dependency graph orders them:
  4. For each stack, the CLI assumes the deploy role and creates a CloudFormation change set: the diff between the live stack and the new template. If the change widens IAM permissions or security groups, it stops and asks (--require-approval; the repo's CI path passes never). Then it executes the change set and streams events to your terminal.
  5. CloudFormation does the work, through the cfn-exec-role. It creates resources in the order of the Ref, GetAtt and DependsOn graph, running independent ones in parallel. During the Data stack it invokes the custom-resource Lambda, which installs the index templates. During the Web stack it resolves the SSM parameters and waits for Beanstalk to launch the instance, whose prebuild hook runs next build.
  6. On failure, CloudFormation rolls that stack back to its previous state; stacks that already finished stay deployed. On success, the CLI prints the stack's outputs (GraphQLApiUrl, AppUrl, …).
What CDK does not do

CDK doesn't track state the way Terraform does. CloudFormation is the state. If someone changes a resource in the console, CDK doesn't know (that's “drift”). And since each deploy is a whole-template diff, a resource you delete from code gets deleted from AWS, unless its DeletionPolicy is Retain, which is exactly why dev, pre-production and production tables use RemovalPolicy.RETAIN.

Tests: synth without the CLI

Because the construct phase is just code, tests can run it directly. test/app.test.ts builds an App in-process and asserts on the result:

infra/test/app.test.ts
import { Match, Template } from 'aws-cdk-lib/assertions';

function synth(envName: string) {
  const { data, api } = buildApp(new App(), { env: envName, account, userPool });
  return { data: Template.fromStack(data!), api: Template.fromStack(api!) };
}

Template.fromStack synthesizes one stack in memory and gives you matchers such as hasResourceProperties('AWS::DynamoDB::Table', {...}), resourceCountIs(...) and Match.objectLike(...). This is the payoff of passing plain values into buildApp instead of reading context deep inside the stacks: the tests need no CLI and no AWS account. Run them with npm test.

Glossary

App
Root of the construct tree; one per CDK program run. Synthesizes on exit.
Construct
Any node in the tree. Signature (scope, id, props). Its path determines the logical ID.
Stack
A construct that becomes one CloudFormation stack and template; the unit of deployment.
L1 / L2 / L3
Raw Cfn* resource / curated resource with defaults and grants / multi-resource pattern.
Props
The typed settings object passed to a construct.
Context
Key/value inputs from -c, cdk.json and cdk.context.json; read with node.tryGetContext.
Feature flag
A @aws-cdk/… context key that opts the project into newer default behavior.
Token
A placeholder for a value known only at deploy time; becomes Ref, GetAtt and so on at synth.
Logical ID
A resource's name inside its template (e.g. ArchiveTable4E5864BF). Changing it means replacing the resource.
Removal policy
What CloudFormation does with a resource when it leaves the template or the stack is destroyed: DESTROY or RETAIN.
Asset
Local files (Lambda code, the app bundle) that CDK stages, hashes and uploads to S3 during deploy.
Cross-stack reference
Using one stack's resource in another stack in the same app; implemented as Export and Fn::ImportValue, and implies a dependency.
Import (from…)
A reference to an existing resource that adds nothing to the template.
Lookup
A synth-time query of your AWS account (e.g. HostedZone.fromLookup), cached in cdk.context.json.
Custom resource
A Lambda that CloudFormation calls on create, update and delete, for things CloudFormation can't do natively.
Cloud assembly
The output of synth (cdk.out/): templates, asset manifests, staged assets and manifest.json.
Bootstrap
The one-time CDKToolkit stack per account and region: asset bucket, deploy, lookup and execution roles.
Change set
CloudFormation's preview of a stack update; cdk deploy creates and executes one per stack.
