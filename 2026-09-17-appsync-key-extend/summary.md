# Session Summary — appsync-key-extend (2026-09-17)

`access/dlp-access` repo, branch `whunter-refactor-appsync-extend`.

## Starting point

The user had manually bumped the AppSync API key's expiration to
2027-09-16 in the AppSync console after noticing the key was only
staying alive as a side effect of frequent CI deploys, not through any
real rotation mechanism.

## Investigation

Traced the AppSync auth config end to end:

- `amplify/backend/api/vtdlp/cli-inputs.json` sets
  `defaultAuthType: { mode: "API_KEY", expirationTime: 7 }`, with
  `AMAZON_COGNITO_USER_POOLS` as an additional auth type.
- The GraphQL transformer compiles this into an `AWS::AppSync::ApiKey`
  CloudFormation resource with a **literal, hardcoded `Expires` epoch**
  computed at `amplify push` time — there's no native rotation feature
  in AppSync/Amplify, just a fixed TTL set once at creation/push.
- The live key gets baked into `src/amplifyconfiguration.json`
  (gitignored, regenerated by `amplifyPush --simple` in the Amplify
  Console build spec on every deploy — confirmed via
  `aws amplify get-app --app-id d1n265krqy0ld3 --query app.buildSpec`).
- Confirmed against the deployment bucket
  (`amplify-vtdlpdev-vtdlppprd-1ccb6-deployment`) and the live AppSync
  API (`77eik3yv7rbdbjhjemas6h7dmi`, app `vtdlp-dev` / `d1n265krqy0ld3`)
  that the key only ever moved forward because deploys happened often
  enough — if the branch goes quiet for more than the TTL, the key
  silently expires and breaks the app.
- `REACT_APP_MINT_API_KEY` in `src/lib/fetchTools.js` is unrelated — it's
  a NOID-minting service key, not the AppSync key.

## What was built

**`infra/appsync-key-rotation/`** — a standalone CDK v2 (TypeScript) app,
kept separate from the Amplify-CLI-owned `amplify/` tree since it manages
the AppSync API from outside that stack:

- `lambda/rotate-api-key/index.ts` — on each scheduled run: lists API
  keys via `appsync:ListApiKeys`; if the newest still-valid key has
  fewer than `MIN_REMAINING_DAYS` left, calls `appsync:CreateApiKey`
  for a fresh one (`KEY_TTL_DAYS`, default 7) and writes it to an SSM
  `SecureString` parameter plus a companion `<param>-expires` parameter;
  also deletes any already-expired keys each run to stay under AppSync's
  50-key cap.
- `lib/appsync-key-rotation-stack.ts` — the Lambda, an EventBridge rule
  (`rate(1 day)` default) triggering it, IAM scoped to
  `ListApiKeys`/`CreateApiKey`/`DeleteApiKey` on the specific API ARN
  and `PutParameter` on the two specific SSM paths, and a CloudWatch
  alarm on Lambda errors optionally wired to an SNS email subscription.
- `bin/appsync-key-rotation.ts` — entrypoint; `apiId` is required CDK
  context, everything else (env name, SSM parameter name, TTLs,
  schedule, alarm email) has defaults or is optional context.

Verified: `npx tsc --noEmit` clean, `npx cdk synth -c
apiId=77eik3yv7rbdbjhjemas6h7dmi -c env=dev -c
alarmEmail=whunter@vt.edu` produces a valid template. **Not deployed.**

**CI wiring** (so the frontend build actually picks up the rotated key
instead of whatever `amplify push` happened to bake in):

- `scripts/sync-appsync-api-key.sh` — if `APPSYNC_API_KEY_SSM_PARAM` is
  set, reads that SSM parameter (with decryption) and overwrites
  `aws_appsync_apiKey` in `src/amplifyconfiguration.json`; no-ops
  cleanly (with a log line) if the env var isn't set, so this is safe
  to land before the CDK stack exists. Verified locally (skip path
  only — no live parameter to read yet).
- `package.json` — added `npm run sync:appsync-key`.
- `examples/amplify.yml` — the repo's checked-in reference build spec;
  inserted `npm run sync:appsync-key` between `amplifyPush --simple`
  and `npm run build`. Note: this file is a reference only — it is
  **not** what the live Amplify Console app actually runs. The live
  spec (fetched via `aws amplify get-app --app-id d1n265krqy0ld3
  --query app.buildSpec`) is separately configured in the console and
  was intentionally left untouched (see Outstanding Tasks).
- `.gitignore` — added `cdk.out/`.

Also confirmed the dev app's build/backend role
(`amplifyconsole-backend-role`) already has `AdministratorAccess`
attached, so no new IAM grant is needed on that side for the sync
script to call `ssm:GetParameter` — this is pre-existing and broader
than this session's scope, not something introduced here; worth a
separate look if anyone wants to scope it down.
